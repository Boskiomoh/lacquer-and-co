# Lacquer & Co.: website rescue and API integration

A deliberately broken small-business website, rebuilt and re-audited, with Stripe, Mapbox, Cal.com and Resend integrated behind honest fallbacks. Lacquer & Co. is a fictional auto detailing studio in Chicago.

## Integrations

| Service | Status on this build | What it does | Fallback when unavailable |
|---|---|---|---|
| Stripe Checkout, test mode | **Live** | Takes the booking deposit on Stripe's hosted page | Booking is held as "deposit pending" with a reference; the flow never dead-ends |
| Mapbox GL JS | **Live** | Opens on the globe, then flies in to the studio once the section is in view. Zoom buttons, a "Back to the workshop" button that flies back after the visitor wanders off, soft blurred edges, palette-matched styling | Static OpenStreetMap image (no token, or JavaScript off) |
| Cal.com API v2 | Demo | Real availability and booking creation | Local slot provider behind the same interface, with a visible "Demo availability" note |
| Resend | Demo | Booking confirmation email, newsletter signup | Logged server-side; the UI says the signup is queued |

### The provider interface

The app never calls a vendor SDK directly. Scheduling and email each sit behind a narrow interface (`lib/providers/scheduling/types.ts`, `lib/providers/email/types.ts`), and a factory picks the real implementation when its environment variables exist and the local one when they do not. The provider exposes `mode: "live" | "demo"`, and the UI shows an honest banner in demo mode.

This buys three things. The demo never dies because a key expired. Swapping Cal.com for another scheduler means writing one file. The integration can be tested without the network.

Stripe deliberately has no fake implementation: a payment provider that silently no-ops is a bad idea even in a demo. The app also refuses to start Stripe with a live key.

### Zod at three boundaries

1. **User input.** Booking details and the newsletter email are validated with one schema, shared by the client form and the route handler.
2. **Vendor responses.** Cal.com payloads are parsed at the boundary, so a shape change fails loudly there instead of scattering `undefined` through the UI (see `tests/calcom-schema.spec.ts`, which includes malformed payloads).
3. **Webhooks.** The Stripe webhook verifies the signature against the raw body first, and only then parses the payload.

### Surviving the Stripe round trip

The booking draft (package, day, time, details, reference) is written to `sessionStorage` as the visitor types, debounced, and parsed through Zod on read, so a draft from an older schema fails closed instead of crashing. A visitor who leaves for Stripe Checkout, cancels, refreshes, or checks their calendar in another tab comes back to the same step with everything filled in. Cancelling at Stripe returns to `/?booking=resume`, which reopens the flow.

After payment, the confirmation page asks the server for the booking status and polls for 60 seconds. If the in-memory booking is gone (a different serverless instance), it rebuilds the confirmation from Stripe session metadata, or from the session draft. The webhook and the confirmation page share one idempotent `confirmPaidBooking`, so whichever arrives first wins and the email is sent once.

Availability is a TanStack Query keyed by package and date, persisted to `sessionStorage`. Switching back and forth between two dates fetches each exactly once (covered by a test). Queries that could hold customer details are never persisted.

## Stack

Next.js 16 (App Router) with TypeScript, Tailwind CSS v4, Zod 4, TanStack Query 5, React Hook Form, Motion, Phosphor icons, Stripe, Mapbox GL JS, Resend, Playwright, Lighthouse and axe-core.

## Running it

```bash
npm install
cp .env.example .env.local     # every variable is optional
npm run dev                    # copies legacy/ to public/before, then starts Next
```

| Script | What it does |
|---|---|
| `npm run build && npm start` | Production build and server |
| `npm test` | Playwright suite: Zod parser unit tests, demo-availability fallback, one fetch per date, inline email error, draft survives refresh |
| `E2E_STRIPE=1 npm test` | Also runs the full booking through Stripe test Checkout with card 4242 4242 4242 4242 |
| `npm run audit -- --label after --path /` | Lighthouse (median of 3 runs by default) plus axe, written to `audit/<label>/` |
| `node scripts/measure-cls.mjs <urls>` | CLS under real network throttling |
| `npm run typecheck`, `npm run lint` | Types and lint |

Webhooks locally: `stripe listen --forward-to localhost:3000/api/webhooks/stripe`, then put the printed `whsec_...` value in `STRIPE_WEBHOOK_SECRET`. Without it, bookings still confirm, because the confirmation page checks the Checkout Session with Stripe directly.

## Decisions and deviations from the PRD

- **Reveals are CSS scroll-driven animations**, not a Motion component. They need no JavaScript, so nothing sits at `opacity: 0` waiting for an observer. Motion is used where state changes: the booking dialog's step transitions.
- **`createAsyncStoragePersister`** over `sessionStorage` instead of the PRD's sync persister, which is deprecated in this TanStack version.
- **`next/image` `fetchPriority="high"`** on the hero instead of `priority`, which Next 16 deprecates.
- **Two palette changes, both from a contrast check.** `ink-faint` darkened from #868A8F (3.1:1) to #5F6369, and a darker text tone for the warning colour. A steel tint was added for quiet bands.
- **Legacy hero weight.** The PRD expected a 4.2 MB hero. The real original photo is 2.82 MB, and that is what the audit reports.
